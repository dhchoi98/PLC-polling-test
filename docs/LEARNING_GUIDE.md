## 1장. 큰 그림 — 이 프로그램이 뭘 하는 거야?

### 비유: 외국인에게 전화해서 숫자 물어보기

```
나 (PC)                          외국인 (PLC)
  │                                  │
  │  "100번 서랍에 뭐 들었어?"       │
  │ ──────────────────────────────▶  │
  │                                  │
  │        "1234가 들었어"            │
  │  ◀──────────────────────────────  │
  │                                  │
  (1234를 화면에 표시)
```

이게 이 프로그램이 하는 전부다.

- **나(PC)** = 이 파이썬 프로그램
- **외국인(PLC)** = 공장에서 기계를 제어하는 장치
- **외국어** = XGT Protocol (PLC가 이해하는 통신 규약)
- **전화선** = RS-232C 시리얼 케이블
- **서랍** = 디바이스 메모리 (D0, D1, D2, ... 번호가 붙은 저장공간)

PLC는 기계를 제어하면서, 자기 내부 메모리(서랍)에 데이터를 저장해둔다.
예: D0 = 생산수량, D1 = 에러코드, M5 = 운전중 여부 등.
이 프로그램은 그 서랍을 **읽기만** 한다. 절대 쓰지 않는다.

### "폴링"이란?

```
시간 →
  0초: "D0 값 뭐야?" → "1234"
  1초: "D0 값 뭐야?" → "1235"     ← 1 올라갔네? 생산 1개 된 듯
  2초: "D0 값 뭐야?" → "1235"
  3초: "D0 값 뭐야?" → "1236"     ← 또 1개
  ...
```

일정 간격으로 **반복해서 물어보는 것** = 폴링(Polling).
PLC가 알아서 알려주는 게 아니라, PC가 계속 물어봐야 한다.

## 2장. 시리얼 통신 — 전화선 연결하기

### RS-232C가 뭔데?

PC와 PLC를 연결하는 **케이블 규격**이다.
요즘은 USB밖에 없으니까, USB-RS232C 변환기를 쓴다.

```
[노트북] ──USB──▶ [USB-RS232C 변환기] ──시리얼 케이블──▶ [PLC]
```

이 변환기를 꽂으면 PC에 **COM 포트**가 생긴다 (COM3, COM4 등).
`scan_serial_ports.py`는 이 COM 포트가 몇 번인지 찾아주는 스크립트다.

### 시리얼 통신 설정값 — 양쪽이 같아야 한다

전화 통화를 하려면 양쪽이 **같은 언어, 같은 속도**로 말해야 한다.

```yaml
# config.yaml
serial:
  port: "COM3"       # 어떤 포트에 꽂았는지
  baudrate: 9600     # 통신 속도 (초당 비트 수) ← PLC 설정과 반드시 일치!
  bytesize: 8        # 데이터 비트
  parity: "none"     # 오류 검출 방식
  stopbits: 1        # 정지 비트
  timeout: 1.0       # 응답 대기 시간 (초)
```

여기서 **baudrate가 제일 중요**하다.
PC가 9600으로 보내는데 PLC가 19200을 기대하면 → 서로 못 알아듣는다.

### 코드에서는?  →  `src/transport/serial_transport.py`

이 파일이 하는 일은 딱 3가지:

```
open()    →  COM 포트를 연다 (전화기를 든다)
send()    →  바이트를 보낸다 (말한다)
receive() →  바이트를 받는다 (듣는다)
close()   →  COM 포트를 닫는다 (전화를 끊는다)
```

내부적으로 `pyserial`이라는 라이브러리를 쓴다.
pyserial이 실제 COM 포트와 대화하는 건 알아서 해주니까 우리는 신경 안 써도 된다.

#### receive()가 하는 일 (조금 더 자세히)

PLC 응답이 몇 바이트인지 미리 모른다. 그래서:

```
1. 첫 바이트 읽기 (ACK=정상 / NAK=에러)
2. ETX(0x03)가 나올 때까지 계속 읽기 (데이터 끝 표시)
3. BCC 2바이트 읽기 (체크섬)
4. 전체를 합쳐서 반환
```

## 3장. XGT Protocol — 외국어 배우기

### 왜 프로토콜이 필요한가?

PLC에 "D0 값 줘"라고 한국어로 보내면 못 알아듣는다.
PLC가 이해하는 **정해진 형식(프로토콜)**으로 바이트를 조립해서 보내야 한다.

LS산전 PLC는 **XGT Cnet Protocol**을 쓴다.

### 요청 프레임 — "질문"을 만드는 법

"D0부터 10개 워드 읽어줘"라는 요청을 XGT 형식으로 만들면:

```
  ENQ  국번   명령  타입  이름길이  디바이스이름    개수  EOT  체크섬
  05   30 30  72   53 42  30 38   25 44 57 ...  30 41  04   XX XX
```

사람이 읽으면 이런 뜻이다:

| 필드 | 바이트 | 의미 |
|------|--------|------|
| ENQ | `05` | "지금부터 질문할게" (시작 신호) |
| 국번 | `00` | 0번 PLC한테 보내는 거야 (RS-232C는 보통 0) |
| 명령 | `r` | 읽기(read). 소문자 r = BCC 포함 |
| 타입 | `SB` | 연속 읽기 (Sequential Block) |
| 이름길이 | `08` | 디바이스 이름이 8글자야 |
| 디바이스 | `%DW00000` | D영역, Word, 0번지 |
| 개수 | `0A` | 10개 읽어줘 (16진수 A = 10) |
| EOT | `04` | "질문 끝" (종료 신호) |
| BCC | `XX` | 체크섬 (데이터가 깨지지 않았는지 확인용) |

### 응답 프레임 — "대답"을 해석하는 법

PLC가 보내는 응답:

```
정상:  ACK  국번  명령  타입  블록수  데이터크기  데이터...  ETX  BCC
에러:  NAK  국번  명령  타입  에러코드                       ETX  BCC
```

- **ACK** (0x06) = "알겠어, 여기 데이터야"
- **NAK** (0x15) = "뭔가 잘못됐어" + 에러코드

### 디바이스 주소 — 서랍 번호 체계

PLC 메모리는 종류별로 나뉜다:

| 디바이스 | 용도 | 크기 | 예시 |
|----------|------|------|------|
| **D** | 데이터 레지스터 | 16비트 (워드) | D0=생산수량, D100=온도 |
| **M** | 보조 릴레이 | 1비트 (ON/OFF) | M0=운전중, M1=에러 |
| **T** | 타이머 | 16비트 | T0=대기시간 |
| **C** | 카운터 | 16비트 | C0=카운트값 |
| **P, K, F** | 기타 비트 | 1비트 | 입출력, 플래그 등 |

코드에서 주소를 XGT 형식으로 변환:
```
("D", 0)     →  "%DW00000"    D영역, Word, 0번지
("D", 100)   →  "%DW00100"    D영역, Word, 100번지
("M", 0)     →  "%MX00000"    M영역, Bit(X), 0번지
```

### BCC(체크섬) — 데이터가 깨지지 않았는지 확인

전화 통화 중에 잡음이 끼면 숫자가 바뀔 수 있다.
BCC는 **"내가 보낸 데이터가 제대로 도착했는지"** 확인하는 장치.

계산법: 모든 바이트를 더한 다음, 256으로 나눈 나머지를 2자리 hex로.

```python
# src/drivers/xgt_protocol.py
def calculate_bcc(frame_bytes: bytes) -> bytes:
    checksum = sum(frame_bytes) % 256
    return f"{checksum:02X}".encode("ascii")
```

예: 바이트 합이 321이면 → 321 % 256 = 65 → "41" → b"41"

## 4장. 코드 구조 — 레이어로 이해하기

### 레이어 비유

```
┌─────────────────────────────────────────────────┐
│  scripts/single_read.py                         │  ← "사장님"
│  "D0부터 10개 읽어서 화면에 보여줘"                │     무엇을 할지 결정
├─────────────────────────────────────────────────┤
│  src/drivers/xgt_protocol.py                    │  ← "통역사"
│  한국어 → XGT 프로토콜 바이트로 변환               │     프로토콜 변환
│  PLC 응답 바이트 → 숫자 리스트로 변환              │
├─────────────────────────────────────────────────┤
│  src/transport/serial_transport.py              │  ← "전화기"
│  바이트를 보내고 받는다                            │     물리적 전송
├─────────────────────────────────────────────────┤
│  RS-232C 케이블                                  │  ← "전화선"
├─────────────────────────────────────────────────┤
│  PLC                                            │  ← "외국인"
└─────────────────────────────────────────────────┘
```

각 레이어는 **자기 아래 레이어만 쓴다**.
스크립트는 드라이버만 알면 되고, 시리얼 통신 세부사항은 모른다.

### 추상 인터페이스 — 왜 base.py가 있나?

`base.py`는 **"규칙서"**다.

```python
# src/drivers/base.py — "PLC 드라이버라면 이것들은 반드시 구현해라"
class PLCDriver(ABC):
    def connect(self): ...
    def disconnect(self): ...
    def read_words(self, device, address, count): ...
    def read_bits(self, device, address, count): ...
```

왜 필요하냐면, 나중에 **다른 PLC 드라이버**(MC Protocol, MEWTOCOL)를 만들어도
스크립트 코드를 안 바꿔도 되게 하려고.

```
지금:   XGTProtocolDriver → LS산전 PLC
나중에: MCProtocolDriver  → 미쓰비시 PLC  ← 같은 read_words() 인터페이스
        MEWTOCOLDriver    → 파나소닉 PLC  ← 같은 read_words() 인터페이스
```

Transport도 마찬가지:
```
지금:   SerialTransport   → RS-232C 케이블
나중에: TCPTransport      → 이더넷 케이블  ← 같은 send()/receive() 인터페이스
```

## 5장. 데이터 흐름 — 코드를 따라가보자

`single_read.py`에서 D0~D9를 읽는 과정을 처음부터 끝까지 추적.

### Step 1: 설정 로드 + 연결

```python
# single_read.py
config = load_config()                    # config.yaml 읽기
transport = SerialTransport(port="COM3")  # 전화기 준비
driver = XGTProtocolDriver(transport)     # 통역사 준비
driver.connect()                          # 전화기 들기 (COM 포트 열기)
```

### Step 2: 읽기 요청

```python
# single_read.py
values = driver.read_words("D", 0, 10)
```

이 한 줄이 내부적으로 하는 일:

```
read_words("D", 0, 10)
  │
  ▼
build_read_request("D", 0, 10)
  │  format_device_address("D", 0, "W")  →  "%DW00000"
  │  프레임 조립: ENQ + 00 + r + SB + 08 + %DW00000 + 0A + EOT
  │  calculate_bcc(프레임)  →  BCC 2바이트
  │  최종: ENQ + 00 + r + SB + 08 + %DW00000 + 0A + EOT + BCC
  │
  ▼
transport.send(요청 바이트)           ← 시리얼로 전송
  │
  ▼
transport.receive()                   ← PLC 응답 수신 대기
  │  ACK 읽기 → ETX까지 읽기 → BCC 읽기
  │
  ▼
parse_read_response(응답 바이트)
  │  BCC 검증 (깨진 데이터 감지)
  │  국번 확인
  │  데이터 hex → 바이트 → 리틀엔디안 16비트 워드로 변환
  │
  ▼
return [1234, 5678, 0, 0, 42, 0, 0, 0, 0, 100]   ← D0~D9 값
```

### Step 3: 결과 출력

```python
# single_read.py
print("[READ] D0=1234, D1=5678, D2=0, ...")
print("[OK] 소요 시간: 47.3ms")
```

## 7장. 핵심 용어 정리

| 용어 | 뜻 | 비유 |
|------|-----|------|

| 래더 프로그램 | PLC 안에서 돌아가는 프로그램 | PLC의 소프트웨어 |
| 디바이스 메모리 | PLC 내부 데이터 저장소 | 번호 붙은 서랍 |
| D 레지스터 | 16비트(0~65535) 저장공간 | 숫자 서랍 |
| M 릴레이 | 1비트(ON/OFF) 저장공간 | 스위치 |
| 폴링 | 주기적으로 반복 읽기 | 1초마다 전화해서 물어보기 |
| 프로토콜 | 통신 규약 (데이터 형식) | 외국어 문법 |
| BCC | 체크섬 (데이터 무결성 확인) | "아까 말한 거 다시 한번?" |
| ENQ/EOT | 프레임 시작/끝 표시 | "여보세요" / "끊을게" |
| ACK/NAK | 정상응답/에러응답 | "알겠어" / "뭐라고?" |
| 국번 (Station) | PLC 식별 번호 | 전화번호 (내선번호) |
| 보레이트 | 통신 속도 (bps) | 말하는 빠르기 |
| 리틀엔디안 | 바이트 저장 순서 (낮은 바이트 먼저) | 1234를 34,12로 저장 |

## 8장. 자주 나올 문제 상황

### "시리얼 포트 열기 실패"
```
[FAIL] 시리얼 포트 열기 실패: could not open port 'COM3'
```
- USB-RS232C 변환기가 안 꽂혀있거나
- COM 포트 번호가 틀렸거나 (scan_serial_ports.py로 확인)
- 다른 프로그램이 이미 그 포트를 쓰고 있거나 (XG5000 등)

### "PLC 응답 없음"
```
[1/2] 시리얼 포트 열림: COM3 @ 9600bps
[FAIL] PLC 응답 없음 (타임아웃)
```
- 보레이트가 PLC 설정과 안 맞거나
- 케이블이 제대로 연결 안 됐거나 (TX/RX 핀 교차 확인)
- PLC 전원이 꺼져있거나

### "BCC 불일치"
```
[ERROR] BCC 불일치: 수신=b'3F', 기대=b'41'
```
- 통신 중 데이터가 깨졌다 (케이블 접촉불량, 전기 노이즈)
- 보레이트가 미세하게 안 맞을 때도 발생

### "NAK 에러"
```
[ERROR] NAK 에러 0x1132: 잘못된 디바이스 메모리
```
- 존재하지 않는 주소를 읽으려 했다
- 디바이스 타입이 틀렸다 (D인데 M으로 읽는다든지)
